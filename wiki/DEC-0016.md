## Context

Rasterization was spread across five call sites (`extract.py:1100,1312,1337,1556`,
`compare.py:85`) plus a separate legacy renderer (`compat/render.py`), each
re-deriving zoom from a single global `rendering.zoom`. Every provider received
the same PNG bytes at the same DPI.

Two problems surfaced while preparing the layout-provider comparison:

1. **The shared DPI suits nobody.** PP-DocLayoutV3 hard-resizes every input to
   800×800 regardless of render DPI (verified: 144/192/300/400 DPI all produce a
   `(1,3,800,800)` tensor). PaddleOCR's PP-DocLayout_plus-L behaves the same way.
   Surya v2, a dynamic-resolution VLM, is the only provider that can use more
   pixels. One global DPI is simultaneously wasteful for the detectors and
   limiting for the VLM.
2. **The `bytes` contract forces redundant codec work.** Measured at 192 DPI on
   page 6 of the mpphys PDF: PNG encode costs 42.1 ms against 4.9 ms to actually
   rasterize (8.6×), and every consumer immediately decodes it again.
   `crop_region_image` decodes the *entire page* once per region — 991 ms for 55
   regions. A 55-region page spent ~1.05 s on image plumbing for ~20 ms of work.

## Decision

Rasterization becomes a first-class, single-owner subsystem.

- A new `render/raster.py` owns `RenderSpec`, `PageRaster`, and `PageRenderer`
  ([[CON-0004]]). `PageRenderer` holds one open `fitz.Document` for the run
  instead of reopening per page.
- The `LayoutProvider` protocol gains a `render_spec: RenderSpec` property.
  `detect(image_bytes: bytes)` becomes `detect(page: PageRaster)`.
- Each rasterization is customized to the requesting provider's spec:
  - `PPDocLayoutV3LayoutProvider` → `target_long_edge=1600, transport="bitmap"`
  - `PaddleOCRLayoutServiceProvider` → `target_long_edge=1600, transport="png"`
  - `SuryaLayoutServiceProvider` → `target_long_edge=2481, transport="png"`
- Rasterize **per spec**, do not render once and downscale. Rasterization is only
  5–10 ms; the cost was never there.
- PNG encoding happens only at the HTTP service boundary, where the wire format
  requires it. In-process providers receive the bitmap directly.
- `crop_region_image` is deleted; callers use `PageRaster.crop_png`.

## Alternatives considered

- **Keep `detect(bytes)`, add an optional `detect_raster`** — rejected: two code
  paths for one contract, and the old path keeps the round-trip alive forever.
- **Render once at max fidelity, downscale per provider** — rejected for
  production: rasterizing directly at the target is crisper than downscaling into
  it, and sharing the raster saves nothing because rasterization is already cheap.
  (Deliberately re-adopted *only* for controlled comparison — see [[DEC-0017]].)
- **Put render specs purely in config** — rejected: a model's preprocessing is a
  property of the model, not of a deployment. Specs live on the provider class;
  config may override them for experimentation.
- **Express the spec as DPI** — rejected: DPI is page-geometry dependent, so the
  same DPI yields different pixel budgets on A4 vs slides. Long-edge pixels are
  what the model preprocessing actually cares about.

## Consequences

**Easier:** each model gets input suited to it; the ~1.05 s/page image plumbing
collapses to ~20 ms; the layout→structured handoff stops being an untyped
`page_state` dict and becomes a typed carrier, improving RUL-0001 conformance.

**Harder:** this is a published-contract change. SPEC.md §5.2 defines
`LayoutProvider` as exactly three methods and ARCHITECTURE.md documents
`detect(image_bytes) -> LayoutResult`; **both must be updated with this decision.**

**Blast radius:** 3 provider implementations, ~9 call sites in `src/`, and ~12
points in tests — two `FakeLayoutProvider.detect` fakes
(`test_phase_c_formula.py:69`, `test_surya_layout_service.py:83,112`) and six
`patch("...render_pdf_page_to_bytes", return_value=...)` sites.

**Unaffected:** the HTTP wire contract still carries base64 PNG, so
`test_surya_layout_service.py:167` (service-side runtime) keeps taking bytes, and
[[DEC-0005]] / [[DEC-0006]] isolation holds — no service runtime is imported
in-process.

**Not addressed here:** `compat/render.py` remains as legacy Known Debt.
