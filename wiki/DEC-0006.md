## Context
A review wrongly claimed `pp-doclayout-v3` was fictional. The model is real in HF
Transformers; the bug was a too-old `transformers` (4.57.6 could not recognize
`pp_doclayout_v3`) and a missing adapter. Separately, the official PaddleOCR
layout runtime (`paddlepaddle`) was wanted for comparison but pulls a conflicting
heavy stack.

## Decision
The in-process default layout provider is `PPDocLayoutV3LayoutProvider`, loaded
**only** through Transformers (`AutoImageProcessor` + `AutoModelForObjectDetection`,
model `PaddlePaddle/PP-DocLayoutV3_safetensors`), with an explicit minimum
`transformers` version guard. No Paddle/PaddleOCR runtime is imported in-process.
PaddleOCR layout is a separate isolated service (DEC-0005) used only for
side-by-side comparison via `compare-layout-page`.

## Alternatives considered
- Introduce PaddlePaddle into the main runtime for PP-DocLayout — rejected:
  unnecessary heavy dependency; the model runs fine through Transformers.
- Drop PP-DocLayout as "fictional" per the review — rejected: the review was
  wrong; the real fix was pinning `transformers==5.5.4` and writing the adapter.

## Consequences
The lower-level Transformers path preserves `polygon_points` and model
`order_seq` (used by DEC-0007 and the reading-order rule). `requirements.txt`
must pin a `transformers` recent enough to recognize the architecture.
PaddleOCR remains opt-in and unproven on this hardware (its `/detect` path was
still failing on the dev machine at last log entry).
