## Context

The PaddleOCR layout service (`layout/paddle_service.py`) loaded weights and
passed `/health` + `/load`, but every `/detect` failed with
`(Unimplemented) ConvertPirAttribute2RuntimeAttribute not support
[pir::ArrayAttribute<pir::DoubleAttribute>] (onednn_instruction.cc:116)`.
The service venv runs CPU-only `paddlepaddle 3.3.1`, whose default CPU path
routes through the PIR → oneDNN executor where this conversion is unimplemented
for PP-DocLayout_plus-L. This was the blocker that had knocked PaddleOCR out of
the layout-model comparison.

## Decision

`PaddleOCRLayoutRuntime.load()` passes `enable_mkldnn=False` to
`LayoutDetection` whenever no GPU is available. Plain (non-oneDNN) CPU inference
executes the model correctly — verified 2026-07-01: 51 regions on the mpphys
page-6 comparison, region distribution closely matching PP-DocLayoutV3.

The same debugging session also fixed result parsing: PaddleX `DetResult` boxes
carry the bbox as a flat `[xmin, ymin, xmax, ymax]` under `coordinate`, which
`_bbox_from_payload` now reads (previously every box was silently dropped,
yielding `200 OK` with 0 regions).

## Alternatives considered

- Env flags (`FLAGS_use_mkldnn=0`, `FLAGS_enable_pir_api=0`) — rejected: not
  honored by the PaddleX predictor path; failure reproduced unchanged.
- Downgrade paddlepaddle below 3.3 — rejected: pins the isolated venv to an old
  runtime for one bug and blocks future fixes.
- Install paddlepaddle-gpu — not pursued now: heavier install, and CPU inference
  is fast enough for comparison purposes; revisit if PaddleOCR becomes default.
- Drop PaddleOCR from the decision set — rejected: the failure was an executor
  bug, not a model-quality signal.

## Consequences

PaddleOCR is usable again as a comparison provider (DEC-0006 keeps it isolated
and out of the in-process runtime). CPU inference forgoes oneDNN acceleration —
acceptable for side-by-side page comparisons; re-evaluate if it is ever promoted
to the default layout provider.
