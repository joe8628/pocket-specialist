## Context
A scanned-PDF smoke test failed with Ollama 404 because the configured production
OCR models (`glm-ocr`, `deepseek-ocr`) were not installed. Surya OCR was available
and would have made the run "pass."

## Decision
Rejected the idea of treating a Surya override success as proof of OCR readiness.
Production config is `glm-ocr` primary with `deepseek-ocr` fallback; their absence
is recorded as a genuine production-readiness gap. Surya override is useful only
to validate the *infrastructure path* (render → layout → crop → OCR → write), not
model readiness.

## Alternatives considered
- Auto-fall back to Surya when production models are missing — rejected: hides a
  real deployment gap and makes "it ran" meaningless for production validation.

## Consequences
A fresh environment must `ollama pull` the production model tags before scanned
PDFs are considered ready. Note the related, still-open contract bug: `glm-ocr`
can echo the prompt's placeholder (`"text": "..."`) and pass structural JSON
validation without producing real OCR — shape validation is not semantic validation.
