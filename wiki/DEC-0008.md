## Context
`GPUScheduler` first used in-process `threading.Lock` / `asyncio.Lock`. But
provider isolation (DEC-0005) means GPU-heavy work runs in *separate processes*
— the main extractor and the UniMERNet/Surya services — which in-process locks
cannot serialize. They could overlap and OOM the single reference GPU.

## Decision
The scheduler keeps its `claim()` / `acquire()` API but backs it with an
OS-level `fcntl.flock` on a shared file (default `/tmp/pocket-specialist-gpu.lock`,
override `PIPELINE_GPU_LOCK_PATH`). Async callers acquire/release via
`asyncio.to_thread(...)`; timeout is non-blocking attempts plus short-sleep
polling until `runtime.gpu_serialization_timeout_s`. This implements DEC-0004
across process boundaries.

## Alternatives considered
- Keep thread/async locks only — rejected: does not serialize separate processes;
  the exact contention provider isolation introduces goes unguarded.
- A broker/daemon arbitrating GPU access — rejected: more infrastructure than a
  single-user local-first tool needs; a file lock is sufficient.

## Consequences
CPU work stays outside the lock; only GPU-heavy sections serialize. One escape
hatch: `ocr.max_parallel_requests > 1` deliberately bypasses the lock for OCR
while layout/formula stay serialized. GPU claim *ordering* is no longer a stable
contract (the DAG owns provider lifecycle), so tests assert claim counts, not order.
