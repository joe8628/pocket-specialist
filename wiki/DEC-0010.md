## Context
Resume needed to be based on graph-node progress, not only linear stage progress,
but the existing stage tables and compatibility code could not be rewritten all
at once. Local-first operation rules out an external DB.

## Decision
Keep SQLite. `set_status(stage, document, page, status, path)` continues to work
**and mirrors** updates into `dag_node_state` (latest state per
`(document, page, node)`). `dag_observations` is an append-only log of node
start/done/failed/retry/compat events. Resume skips `done`, retries `failed`
until `MAX_RETRIES`, treats missing state as processable, and computes the next
page from the first processable page. `status` reports both stage and DAG
summaries.

## Alternatives considered
- New `checkpoint_stage` metadata key — rejected (DEC-0013): duplicated existing
  concepts and invented an unnecessary metadata convention.
- Rewrite all compatibility code onto DAG nodes immediately — rejected: too large
  and risky; mirroring lets both models coexist during migration.

## Consequences
Observation metadata reuses existing task/unit/provenance naming (`doc_id`,
`unit_id`, `task_id`, `task_type`, `source_stage`, optional `artifact_uri`), typed
`dict[str, object]`. `should_process_node()` reads `MAX_RETRIES` at call time, not
as a default arg, so runtime/test overrides are honored. Aggregate `document.json`
must be rebuilt from existing per-page artifacts on resume (see DEC-0009).
